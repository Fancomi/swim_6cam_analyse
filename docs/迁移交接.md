## 0. 项目一句话

六路相机拼接全景视频（5002×2102）的**游泳分析**：检测（yolo26 微调）→ 跟踪（IoU 贪心）→
RTMPose 关键点 → 划水计数与速度。提供 **Python 参考实现**（Plan A/B/C）与 **C++/CUDA 实时实现**
（Plan C 全链路 GPU 驻留，Windows 实测 65~71 fps 纯分析 / 27~35 fps 渲染，见 §2）。

## 2. 当前状态

### 迁移已完成（2026-08-13，Windows 侧实测）

Windows 全链路已跑通：构建 → 导出 ONNX → 建 engine → 全量 3000 帧纯分析 + 渲染。

**实测环境**：RTX 4080 Laptop（12 GB，驱动 571.96，sm_89）、CUDA 12.8、
TensorRT 10.11.0.33、vcpkg OpenCV 4.10（C++ 侧）、VS 2022、Python 3.10.11 + torch 2.1.0+cu121。

| 模式 | 端到端 | 每帧 | 说明 |
|---|---|---|---|
| 纯分析 | **65–71 fps** | 14.2–15.5 ms | GPU 段 7.0–7.9 ms（`1_pre+detect` 5.3–5.6 + `2_crop+pose+decode` 1.7–2.0 + `7_track_metrics` 0.3），其余 7.1–8.0 ms 是 `0_src_wait` 等解码 |
| 渲染（`--out`） | **27–35 fps** | 29.0–37.6 ms | `0_src_wait` 涨到 18.6–25.2 ms（libx264 与解码抢 CPU），`8_frame_d2h` 已被 event 重叠到 0.02 ms |

> 给区间而非单值：笔记本同命令连跑三次差 10% 属常态（散热 + 后台进程），渲染模式
> 波动更大因为多一个 libx264 进程。GPU 段自身稳定在 7.5–8 ms。

3000 帧结果：24107 人次、63 个 track、划水合计 381 次；**纯分析与渲染模式的
JSON 与 `--dump` CSV 均逐字节一致**。
渲染产物 `output/win_render_3000f.mp4`（h264 5002×2102，3000 帧，1.12 GB）
`ffmpeg -f null -` 全量解码无错误，抽帧目视骨架/ID/速度标注正常。

> 上面这组数与 8 月 13 日之前记录的 50.5/30.5 fps、24249 人次、592 次划水都不同，
> 原因有三，都不是回归：解码换成自建 `CreatePipe` 的 ffmpeg 管道（16.9 → 13.0 ms/帧，
> 且像素值与 MSMF 不同）、划水算法全面对齐 Python（拓扑 prominence + 自适应窗）、
> engine 按新身份戳重建导致 fp16 级 tactic 差异。

显存：进程运行期整卡占用从 1830 MiB 升到 2824 MiB，即**本进程约 1.0 GB**（含 CUDA context）；
detect engine 工作区 56.2 MB，pose engine 工作区 153.4 MB（batch≤40）。

> 对照 H800（Linux）：纯分析 71–80 fps / 12.4–14.1 ms。Windows 略慢，
> 差距主要在 `1_pre+detect`（5.66 vs 4.49 ms）与 CPU 解码，属笔记本卡的正常水平。
> engine 工作区大小也与 H800 不同（56/153 MB vs 56/94 MB），因为 TRT 按 GPU 选 kernel。

- **分支**：只有 `cpp-realtime-clean`（权重不入库、历史干净 844KB，未来整体合入 `main`）。
  含 LFS 权重的旧分支 `cpp-realtime` 已删除：它的内容已被本分支覆盖，唯一"多出"的
  就是那四个权重指针文件。权重靠 zip/外部提供，来源与复现见 `docs/权重来源与复现.md`。
- **Windows 适配改动**见下面 §3.1 的坑位清单。
- **已完成的排查（Linux 期）**：C++ 检测输出与 Python（同模型同参数）逐帧一致；"框闪"根因是
  渲染帧环少一格 → 已修复并全量重渲染验证（见 git log `470a09d`）。

### 3.1 Windows 迁移踩过的坑（改动均已提交）

1. **`#include <dlfcn.h>` 在 MSVC 不存在** —— `frame_source.cpp` 原有一段
   `dlopen("libnvcuvid.so")` 的 NVDEC 探测。现已整段删除：探到 dll 也不代表能解本画布
   （5002 > 4096 上限），判据本身是错的，改为直接用 ffprobe 报的真实宽高与 4096 比。
2. **TRT 库名带 `_10` 后缀** —— `find_library(nvinfer)` 在 Windows 找不到，
   已改 `NAMES nvinfer nvinfer_10`（同理 nvonnxparser）。
3. **源码是 UTF-8 无 BOM，MSVC 默认按 ACP(936) 解析** —— 中文注释的字节会被吃进语法。
   已给 `/utf-8`（CXX）与 `-Xcompiler=/utf-8`（CUDA）；运行期 `main()` 调
   `SetConsoleOutputCP(CP_UTF8)` 让控制台中文不乱码。**与全局 CLAUDE.md 里 `.ps1`
   无 BOM 的坑同源，改这些文件时不要整文件读写。**
4. **`windows.h` 的 min/max 宏** —— 会打断 `std::max` 与 OpenCV 模板调用，
   include 前必须 `#define NOMINMAX`（`main.cpp` 与 `frame_source.cpp` 都加了）。
5. **装 torch 会把 numpy 顶到 2.x** —— `import torch` 报
   `Failed to initialize NumPy: _ARRAY_API not found`（torch 的 C 扩展按 numpy1 ABI 编译）。
   必须在装 mmcv/mmpose **之前** `pip install numpy==1.26.4 "setuptools<81"`。
6. **vcpkg 的 opencv4 没有 ffmpeg 特性** —— C++ videoio 只剩 MSMF/DSHOW，而 MSMF 的
   H.264 编码器在 1920×1080 / 3840×2160 能开，**在画布 5002×2102 直接
   `isOpened()==false`**（读 5002×2102 没问题，只是写不了）。
   `main.cpp` 的 `Writer` 已加回退：OpenCV(`avc1`→`mp4v`) 都开不了时，
   起一个 `ffmpeg` 子进程用管道喂 rawvideo（`-c:v libx264 -preset veryfast -crf 23`），
   所以**渲染模式要求 `PATH` 里有 ffmpeg**。
   顺带好处：编码在独立进程里跑，与本进程的 GPU 推理天然并行。
   读侧同理已改走 ffmpeg 管道（不只是快，MSMF 的像素值也与 Python 的 cv2 不一致，
   见 §6 第 2 条），所以**纯分析模式也建议 `PATH` 里有 ffmpeg/ffprobe**，
   探测不到才回退 MSMF。
7. **本机 NVENC 用不了** —— 驱动 571.96 只提供 NVENC API 13.0，ffmpeg 8.1 要求 13.1
   （报 `Driver does not support the required nvenc API version`，退出码 -22）。
   所以编码器定为 libx264；换新驱动后可考虑 `-c:v h264_nvenc` 提速。
8. **`install.sh` 自检引用了不存在的模块** —— `swim_analyse.pipeline` 不存在，
   已改成 `swim_analyse.cli, swim_analyse.plans`。
9. **`export_onnx.py` 会在 `weights/` 下留一个中间 `yolo_swim_detect.onnx`** ——
   ultralytics 先写在 .pt 旁边再 `os.replace`，可手动删掉。

## 6. 已知事项 / 待办

1. ~~**`--max-persons <40` 会崩**~~：**已修复**。真因不是 engine batch 上限（pose engine
   的动态 batch 是 1..40，传更小的 batch 本就合法），而是 `k_dedup_boxes` 里用编译期上限
   `kMaxPersons` 当容量读写，`--max-persons` 更小时 `boxes/conf` 越界 → 进程直接
   `0xC0000409`（STATUS_STACK_BUFFER_OVERRUN）。现在 `cap` 由调用方传入并在 kernel 内
   夹紧。engine 缓存也已按身份戳（SM + TRT 运行期版本 + max_batch + 精度 + onnx
   mtime/size）分文件，换 `--max-persons` 不会静默复用不匹配的 engine。
2. **NVDEC 对本画布不可用（非"未实现"）**：CUVID 的 H.264 8bit 规格上限是
   4096×4096，而画布宽 5002，硬解无论如何都开不了（HEVC 上限 8192，但源是 H.264）。
   真正的提速方向是绕开 OpenCV 的 videoio，**已落地**：默认走外部 `ffmpeg` 管道
   （自建 `CreatePipe` 128 MB 缓冲）13.0 ms/帧，对比 OpenCV(MSMF) 16.9 ms/帧；
   ffmpeg CLI 自身地板是 12.9 ms/帧，已无余量。注意两条路径**解出的像素值不同**
   （MSMF 与 swscale 的 YUV→BGR 矩阵不同，逐像素平均差约 4.5/255），
   只有 ffmpeg 路径与 Python `cv2` 逐字节相同，`--decoder cpu` 仅作兜底排障。
3. **解码已是纯分析模式的瓶颈**（`0_src_wait` 占 49%，7.42 ms/帧）：下限就是 ffmpeg
   自身的 12.9 ms/帧，预取只能与 GPU 段重叠、消不掉。再快只有 live 走 `RawSource`
   （拼接程序直接给显存帧）或 ffmpeg 输出 yuv420p 把搬运减半后在 kernel 转 BGR ——
   后者会丢掉与 Python 的逐字节一致性（swscale 是 BT.601 limited range），故未采用。
4. **渲染模式瓶颈在 CPU 编码**（实测 27~35 fps）：`8_frame_d2h` 经 `cudaEvent` 重叠后只剩
   0.02 ms/帧，开销全在 libx264，且编码进程与解码进程抢 CPU（`0_src_wait`
   从 7.42 涨到 25.2 ms）。参照系：单用 ffmpeg 做一次「解码 + libx264 重编码」不带任何
   分析就要 32.8 ms/帧，我们带分析带渲染 37.6 ms/帧，即推理+跟踪+绘制只多花 4.8 ms/帧。
   本机 NVENC 因驱动 API 版本过旧不可用（§3.1 第 7 条）；
   换新驱动后把 `Writer` 的 ffmpeg 命令改 `-c:v h264_nvenc` 即可，或降渲染分辨率。
5. **`data/20260629/` 未打包**：Plan A（跨相机 mesh）需要它；Plan B/C 与 C++ 链路不需要。
6. **engine/onnx 不入库**：`cpp/models/*.onnx|*.engine` 在 .gitignore，Windows 首次运行
   自动从 weights 导出+构建。
7. **core 文件**：Linux 上 `core.3479244`（7.7G，崩溃转储）可删，不影响迁移。

## 7. 调试技巧

- **对照验证**：C++ `--dump` 导出逐帧框 → 与 Python 同参数重跑结果对比（两者应逐帧一致）。
  Python 侧 `output/merged_3000f/cache.pkl` 是**旧模型产物**，不要作为基准。
- **纯分析 vs 渲染必须同结果**：两种模式的 `--json` 应逐字节一致
  （Windows 已验证）。不一致说明渲染路径动了帧缓冲，参考 `c19b3c0` 那个帧环 bug。
- **渲染产物校验**：`ffprobe` 看帧数/分辨率，再 `ffmpeg -i out.mp4 -f null -` 全量解码
  确认无坏帧（走 ffmpeg 管道时若中途断流，这里会暴露）。
- **效率验证**：`--show-fps` 看实时帧率；GPU 占用用 `nvidia-smi`。
- **显存**：C++ 全链路 GPU 驻留 + 显存预分配（零 cudaMalloc）。
  Windows 实测整进程约 1.0 GB（含 CUDA context），用运行前后的
  `nvidia-smi --query-gpu=memory.used` 差值量；`--query-compute-apps=used_memory`
  在 Windows WDDM 下返回 `[N/A]`，别用它。
- **Windows 注意**：路径分隔符 `\`；bash 脚本（run.sh/install.sh）用 Git Bash 执行，
  或直接调 CLI 参数。中文输出乱码先查是不是漏了 `/utf-8` 或 `SetConsoleOutputCP`。
