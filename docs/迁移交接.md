## 0. 项目一句话

六路相机拼接全景视频（5002×2102）的**游泳分析**：检测（yolo26 微调）→ 跟踪（IoU 贪心）→
RTMPose 关键点 → 划水计数与速度。提供 **Python 参考实现**（Plan A/B/C）与 **C++/CUDA 实时实现**
（Plan C 全链路 GPU 驻留，目标 71fps 纯分析 / 21fps 渲染）。

### 迁移已完成（2026-08-13，Windows 侧实测）

Windows 全链路已跑通：构建 → 导出 ONNX → 建 engine → 全量 3000 帧纯分析 + 渲染。

**实测环境**：RTX 4080 Laptop（12 GB，驱动 571.96，sm_89）、CUDA 12.8、

|---|---|---|---|
| 纯分析 | **50.5 fps** | 19.8 ms | GPU 段 11.9 ms（`1_pre+detect` 8.27 + `2_crop+pose+decode` 3.58 + `7_track_metrics` 0.11） |

显存：进程运行期整卡占用从 1830 MiB 升到 2824 MiB，即**本进程约 1.0 GB**（含 CUDA context）；

> engine 工作区大小也与 H800 不同（61/153 MB vs 56/94 MB），因为 TRT 按 GPU 选 kernel。

  **Windows 请用 `cpp-realtime-clean`**——代码秒下，权重靠 zip/外部提供。
  权重来源与复现见 `docs/权重来源与复现.md`。
- **Windows 适配改动**见下面 §3.1 的坑位清单。
- **已完成的排查（Linux 期）**：C++ 检测输出与 Python（同模型同参数）逐帧一致；"框闪"根因是

**TensorRT Windows 安装要点**：解压 zip 即可（实测 `D:/WindowsProject/workspace/TRT/TensorRT-10.11.0.33`）。
Windows 版导入库名**带版本后缀**：`nvinfer_10.lib` / `nvonnxparser_10.lib`，

RTX 30 系=`86`。**不要**用默认的 `86 89 90`（不含 50 系，且多架构编译慢很多）。

### 3.1 Windows 迁移踩过的坑（改动均已提交）

1. **`#include <dlfcn.h>` 在 MSVC 不存在** —— `frame_source.cpp` 的 NVDEC 探测原是
   `dlopen("libnvcuvid.so")`，已按 `#ifdef _WIN32` 改成 `LoadLibraryA("nvcuvid.dll")`。
2. **TRT 库名带 `_10` 后缀** —— `find_library(nvinfer)` 在 Windows 找不到，
   已改 `NAMES nvinfer nvinfer_10`（同理 nvonnxparser）。
3. **源码是 UTF-8 无 BOM，MSVC 默认按 ACP(936) 解析** —— 中文注释的字节会被吃进语法。
   已给 `/utf-8`（CXX）与 `-Xcompiler=/utf-8`（CUDA）；运行期 `main()` 调
   `SetConsoleOutputCP(CP_UTF8)` 让控制台中文不乱码。**与全局 CLAUDE.md 里 `.ps1`
   无 BOM 的坑同源，改这些文件时不要整文件读写。**
4. **`windows.h` 的 min/max 宏** —— 会打断 `std::max` 与 OpenCV 模板调用，
   include 前必须 `#define NOMINMAX`（`main.cpp` 与 `frame_source.cpp` 都加了）。
5. **装 torch 会把 numpy 顶到 2.x** —— `import torch` 报
   `Failed to initialize NumPy: _ARRAY_API not found`（torch 的 C 扩展按 numpy1 ABI 编译）。
   必须在装 mmcv/mmpose **之前** `pip install numpy==1.26.4 "setuptools<81"`。
6. **vcpkg 的 opencv4 没有 ffmpeg 特性** —— C++ videoio 只剩 MSMF/DSHOW，而 MSMF 的
   H.264 编码器在 1920×1080 / 3840×2160 能开，**在画布 5002×2102 直接
   `isOpened()==false`**（读 5002×2102 没问题，只是写不了）。
   `main.cpp` 的 `Writer` 已加回退：OpenCV(`avc1`→`mp4v`) 都开不了时，
   起一个 `ffmpeg` 子进程用管道喂 rawvideo（`-c:v libx264 -preset veryfast -crf 23`），
   所以**渲染模式要求 `PATH` 里有 ffmpeg**。
   顺带好处：编码在独立进程里跑，与本进程的 GPU 推理天然并行。
7. **本机 NVENC 用不了** —— 驱动 571.96 只提供 NVENC API 13.0，ffmpeg 8.1 要求 13.1
   （报 `Driver does not support the required nvenc API version`，退出码 -22）。
   所以编码器定为 libx264；换新驱动后可考虑 `-c:v h264_nvenc` 提速。
8. **`install.sh` 自检引用了不存在的模块** —— `swim_analyse.pipeline` 不存在，
   已改成 `swim_analyse.cli, swim_analyse.plans`。
9. **`export_onnx.py` 会在 `weights/` 下留一个中间 `yolo_swim_detect.onnx`** ——
   ultralytics 先写在 .pt 旁边再 `os.replace`，可手动删掉。

## 6. 已知事项 / 待办

1. **`--max-persons <40` 会崩**：pose engine 的 batch 上限在构建时固定（默认 40）。
   要支持低显存（如 20 人上限），需在 `main.cpp` 里把 engine 缓存文件名按 batch 参数化
   （如 `pose_b20.engine`），并在重建时用对应 opt/max batch 构建。4080 Laptop（12GB）上
   当前 40 人上限完全够用（实测每帧最多 14 人，整进程 ~1.0 GB），非必须。
2. **NVDEC 未实现**：Windows 侧探测已改成 `LoadLibraryA("nvcuvid.dll")`（本机探测通过），
   但 vcpkg/apt 的 OpenCV 都没编 `cudacodec`，所以仍走 CPU 解码。
   纯分析的剩余开销主要在 CPU 解码（5002×2102 约 19 ms/帧，已被预取线程部分掩盖），
   接上 NVDEC 或用 `RawSource` 可进一步提速。
3. **渲染模式瓶颈在编码与整帧 D2H**（Windows 实测 30.5 fps）：
   `8_frame_d2h` 3.24 ms/帧，其余是 CPU 绘制 + libx264。
   本机 NVENC 因驱动 API 版本过旧不可用（§3.1 第 7 条）；换新驱动后把 `Writer` 的
   ffmpeg 命令改 `-c:v h264_nvenc` 即可，或降渲染分辨率。
4. **`data/20260629/` 未打包**：Plan A（跨相机 mesh）需要它；Plan B/C 与 C++ 链路不需要。
5. **engine/onnx 不入库**：`cpp/models/*.onnx|*.engine` 在 .gitignore，Windows 首次运行
   自动从 weights 导出+构建。
6. **core 文件**：Linux 上 `core.3479244`（7.7G，崩溃转储）可删，不影响迁移。

## 7. 调试技巧

- **对照验证**：C++ `--dump` 导出逐帧框 → 与 Python 同参数重跑结果对比（两者应逐帧一致）。
  Python 侧 `output/merged_3000f/cache.pkl` 是**旧模型产物**，不要作为基准。
- **纯分析 vs 渲染必须同结果**：两种模式的 `--json` 应逐字节一致
  （Windows 已验证）。不一致说明渲染路径动了帧缓冲，参考 `c19b3c0` 那个帧环 bug。
- **渲染产物校验**：`ffprobe` 看帧数/分辨率，再 `ffmpeg -i out.mp4 -f null -` 全量解码
  确认无坏帧（走 ffmpeg 管道时若中途断流，这里会暴露）。
- **效率验证**：`--show-fps` 看实时帧率；GPU 占用用 `nvidia-smi`。
- **显存**：C++ 全链路 GPU 驻留 + 显存预分配（零 cudaMalloc）。
  Windows 实测整进程约 1.0 GB（含 CUDA context），用运行前后的
  `nvidia-smi --query-gpu=memory.used` 差值量；`--query-compute-apps=used_memory`
  在 Windows WDDM 下返回 `[N/A]`，别用它。
- **Windows 注意**：路径分隔符 `\`；bash 脚本（run.sh/install.sh）用 Git Bash 执行，
  或直接调 CLI 参数。中文输出乱码先查是不是漏了 `/utf-8` 或 `SetConsoleOutputCP`。
